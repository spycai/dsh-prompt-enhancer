# 超时问题结案说明

日期：2026-11-14
结论：**不是插件缺陷，是 `hy4free` 模型的固有限制。**

---

## 一、事实链

| 证据 | 结果 |
|---|---|
| 用假 `ctx.llm` 跑真实 `apply()` | **45ms 返回 200**，只调一次模型 —— 插件逻辑无问题 |
| 用户换其他模型 | **正常，不超时** —— 排除路由、鉴权、网络 |
| 用户用 `hy4free` | 超时 |

## 二、根因

`~/.dsh/profiles/desktop/cordis.patch.yml` 里两个 Hy4 型号的声明不同：

```yaml
# hy4free（用户使用的）
reasoning:
  supportedEfforts: [high]      # ← 只有 high 一档
  defaultEffort: high
  canDisableThinking: false     # ← 不能关

# hy4std
reasoning:
  supportedEfforts: [low, high] # ← 可以降到 low
  defaultEffort: high
  canDisableThinking: false
```

**`hy4free` 只支持 `high`**。所以：

- 设 `reasoningEffort: low` → 会报 `unknown reasoning effort`，不解决问题
- 设 `maxTokens: 4000` → 只限制「思考+输出」的总量，**不能加快思考速度**
- 加长客户端超时 → 只是等得更久，可能仍然不够

**结论：hy4free 的慢是模型自身行为，插件侧没有任何参数能改变它。**

---

## 三、这轮排查中我们做对和做错的事

### 做对了

1. **先用假模型隔离变量**：45ms 返回 200，立刻排除插件代码，避免在错误方向上改代码
2. **换模型对照**：这是最终定性的关键一步
3. **保留 240 秒超时**：虽然对 hy4free 可能仍不够，但对其他推理模型是必要的

### 做错了（已修）

| 问题 | 版本 | 说明 |
|---|---|---|
| `maxTokens: 1400` 太小 | v1.5.6 修 | 推理 token 也计入该预算，1400 几乎全被思考吃掉 |
| 在关键路径 `await llm.resolveModelInfo` | v1.6.1 撤回 | 该调用委托 `adapter.resolveModel`，**可能发网络请求**——修超时的代码自己制造了新挂起 |
| 「从成功响应学习超时」 | v1.6.1 撤回 | 超时后 `.then()` 不执行，**永远学不会**，第一次点击永远是短超时 |

**核心教训：超时控制本身绝不能引入新的阻塞点。**

---

## 四、用户该怎么办

| 场景 | 做法 |
|---|---|
| 想稳定用提示词增强 | **换成非推理模型**（DeepSeek 系列等） |
| 坚持要用推理模型 | 选 `hy4std` 并把 `reasoningEffort` 设成 `low`（它支持）；`hy4free` 无解 |
| 只是想等 | 240 秒上限已给足，但 hy4free 可能仍不够 |

---

## 五、插件侧的可改进空间（未做，记录备查）

当前插件**无法感知模型是否会慢**，只能给统一 240 秒。若将来要改进：

1. **启动时读一次模型元数据并缓存**（不放在请求路径上），据此给出提示
2. **UI 上标注**：「当前模型为高推理强度，改写可能较慢」
3. **提供快速模式**：检测到 reasoning 模型时，自动附加一句「请直接给出结论，不要展开推理」——但**对 `canDisableThinking: false` 的模型效果未经验证**

这三条都需要真机验证，不建议在没有可复现环境时贸然实现。
