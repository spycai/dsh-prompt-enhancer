## 二、关键许可证分析

### 2.1 f/prompts.chat 是唯一可安全内置的数据源

它的 `LICENSE` 是**双许可**，原文：

> - **Source code and site-authored content** … is licensed under the MIT License.
> - **Prompt content and data** (prompts.csv, PROMPTS.md, and all user-submitted prompt text) is dedicated to the public domain under **CC0 1.0 Universal**.
> - If you are unsure which license applies to a particular file, the MIT License applies by default.

**判定**：
- `prompts.csv` 明确属于 CC0 1.0 → **公有领域，可自由复制、修改、再分发，无需署名**
- GitHub 把它标为 `NOASSERTION` 是因为双许可非标准组合，**不代表有风险**
- 已实际读取 `LICENSE-CC0` 文件，确认是标准 CC0 1.0 法律文本 → 证据充分

### 2.2 其余候选的许可判断

| 项目 | 判定 | 理由 |
|---|---|---|
| TheBigPromptLibrary (MIT) | 可用但**不建议内置** | MIT 要求保留版权声明；且含 Jailbreak 目录，内容质量与安全性不适合普通用户 |
| LangGPT (Apache-2.0) | **可借鉴不可抓取** | Apache-2.0 要求保留 NOTICE，且它本身是文档项目，抓文档当提示词无意义 |
| voyager (GPL-3.0) | **明确不用** | GPL 传染性会迫使整个插件开源，与 MIT 发布冲突 |
| GPT-Prompter (MIT) | **只借鉴交互** | 技术栈不同（浏览器扩展 vs DSH 插件） |

### 2.3 许可风险清单

| 风险 | 处置 |
|---|---|
| 双许可文件按错分支使用 | 只取 `prompts.csv`（明确 CC0），不取 `src/` 下代码 |
| 把 CC0 数据误标为需署名 | 记录中标注 CC0 且不强制署名，但**仍保留来源字段**便于追溯 |
| 未来接入非 CC0 源 | 数据结构强制带 `license` 字段，**只有允许再分发的许可证才入库**，其余拒绝 |
| 用户收藏内容含第三方版权 | 收藏只存引用 id，不复制正文 |

## 三、复用结论

| 部分 | 结论 | 说明 |
|---|---|---|
| **种子库数据** | **复用**（f/prompts.chat，CC0） | 直接内置一份精简快照，离线可用 |
| **联网刷新** | **自研** | 官方无 API，按 `prompts.csv` 的 raw 地址拉取并校验 |
| **面板/交互** | **自研** | DSH slot 机制独有，无可复用组件 |
| **提示词改写逻辑** | **全自研** | 沿用 v1.7.0 已有的 `SYSTEM_PROMPTS` + nonce 注入防护 |
| **结构化提示词写法** | **借鉴** LangGPT 理念 | 仅作为文案与字段设计参考，不复制内容 |

### 3.1 为什么核心逻辑必须自研

1. **宿主体制独有**：DSH 的 slot / connection Fetch / 鉴权模型在开源界没有等价物
2. **没有可复用的"想法→专业提示词"实现**：搜索到的项目要么是**静态数据集合**（prompts.chat、TheBigPromptLibrary），要么是**浏览器端注入工具**（GPT-Prompter、voyager），都没有"输入一句想法→生成适配提示词"这条链路
3. **许可污染风险**：能提供该能力的项目（voyager）是 GPL-3.0，采用会污染我们 MIT 的发布

### 3.2 中文场景的现实

调研中**没有找到许可证清晰、可直接内置的中文提示词库**：
- `funNLP`（84k 星）是 NLP 工具集，非提示词库，且无许可证标注
- `LangGPT` 是方法论
- 其余中文项目多为教程/资源导航

**结论**：种子库以英文为主（来自 CC0 源），但**生成结果是中文**——因为改写由模型完成，语言跟随用户输入。种子库在这里的作用是"结构与思路参考"，不是直接输出给用户看的成品。

## 四、前沿技术路径评估（用户额外要求）

| 方向 | 可行性 | 建议 |
|---|---|---|
| **本地向量检索（语义搜索宝库）** | 中 | 需要 embedding 模型，插件是纯 Node 无依赖树，引入成本高。**v1.8 先做关键词+标签检索，语义留作 v1.9** |
| **提示词组合（Decorator 模式）** | 高 | 借鉴 `prompt-decorators` 思路，但需要 UI 改动，**留作 v1.9** |
| **DSPy 式自动优化** | 低 | 需 Python 与训练设施，与插件架构冲突。**只作为离线评估方法**（我们已有门禁） |
| **结构化输出（三段式）** | 高 | v2 设计稿已就绪（`产出/v2设计稿/`），但需 UI 配合，**不在 v1.8 范围** |

**v1.8 的定位**：把"按钮"升级为"面板"，把"单次改写"扩展为"可参考宝库的改写"。技术选型保守，风险可控。

## 五、对实施的影响（给第 2 步的输入）

1. **种子库**：内置一份 `prompts.chat` 的精简快照（不内置 10.9MB 全量，取精选 + 分类）
2. **联网刷新**：默认关闭，用户手动触发才拉；失败静默回落种子库
3. **数据结构必须含**：`id / title / category / body / source / license / fetchedAt`
4. **许可过滤**：解析时校验 `license` 字段，非 CC0/MIT/Apache-2.0 白名单的一律丢弃
5. **不写爬虫**：只按 raw 地址取结构化文件，不解析 HTML
