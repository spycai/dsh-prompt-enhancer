# 下一步功能规划（基于 GitHub 调研）

日期：2026-11-14
基线：dsh-prompt-enhancer **v1.5.6**（`9419c84`）
调研方法：GitHub 搜索 + 逐个读 README/详情，不凭印象

---

## 一、先看清竞争格局

### 1.1 存在一个直接对标产品

| 项 | 我们 | [x118111/prompt-optimizer](https://github.com/x118111/prompt-optimizer) |
|---|---|---|
| 形态 | `conversation.input.right` 插槽按钮 | 同位置 ✨ 按钮 |
| stars | — | 1 |
| 最后更新 | 2026-11-14（今天） | 2026-08-14（三个月前停更） |
| 改写方式 | 单次 `llm.stream` | 同 |
| **上下文** | **不带对话历史** | **自动带最近 8 条对话** |
| 模型回退 | 有（config → selection） | 有（selection → 首个可用 provider） |
| 错误可见性 | 有（code 映射 + 文案） | 有 |
| 测试 | 83 条 | 无 |
| 质量评估 | 40 条用例 + 门禁 | 无 |

**结论**：它停更且无测试，但**有一个我们明确缺的能力——对话上下文**。

这是本次调研最有价值的一条发现：**用户在同一会话里已经聊了几轮，插件却只看当前草稿**。这会导致改写跑偏。例如前面几轮已经说清是"给客户看的"，草稿只写"做个PPT"，我们却会问受众。

### 1.2 值得借鉴的机制（非同类产品）

| 项目 | stars | 可借鉴的机制 | 落到我们哪里 |
|---|---|---|---|
| [PromptEnhancer](https://github.com/Hunyuan-PromptEnhancer/PromptEnhancer)（腾讯混元，CVPR 2026） | 3805 | **Chain-of-Thought Prompt Rewriting**：先推理"用户真正要什么"，再产出改写，而不是一步到位 | 直接对应我们 v2 设计稿的 Pass 1「分析→合成」两段式。**论文可作为设计依据引用** |
| [prompt-decorators](https://github.com/smkalami/prompt-decorators) | 479 | **装饰器**：把增强拆成可组合的独立单元（`+++Reasoning` `+++StepByStep`），用户按需组合 | 我们的"两种模式"可以扩展成**可组合能力开关**：`+上下文` `+反例` `+输出格式` `+约束清单` |
| [LLMLingua](https://github.com/microsoft/LLMLingua)（微软） | 6822 | 提示词**压缩**：在保留信息的前提下减 token | 反向能力：草稿太长时先压缩再改写（我们有 `maxInputChars: 12000`，但没有压缩） |
| [prompty](https://github.com/microsoft/prompty)（微软） | 1289 | 提示词作为**可评估资产**：版本、调试、评估一体化 | 我们已有评估门禁，可补"提示词版本化 + 变更记录" |

### 1.3 领域区分（避免抄错）

`Hunyuan-PromptEnhancer` 虽然名字最像，但它是**文生图**提示词改写（`text-to-image`），解决的是"让出图更准"。我们解决的是"让对话/任务更准"。**只能借机制，不能借内容**。

## 二、按「证据强度 × 可行性」分层

### P0 · 补上明确的能力缺口

#### F1 对话上下文感知

**为什么做**：竞品有、我们没有；这是真实体验差异，不是猜测。

**怎么做**：
- Client 侧已有 `useConversation` / `useProjection` 等 props（`conversation.input.right` 插槽的 `standardProps` 里列了 `useChat`、`useConversation`、`useTrajectory`）
- 取最近 N 轮（建议 4 轮）压缩成简短摘要随请求发给 Host
- Host 拼进 system 或作为额外的 `<context>` 块
- **关键约束**：只能作为"背景参考"，不能让上下文覆盖用户当前草稿的明确要求

**风险**：上下文会显著增加 token（多轮对话可能几千 token），直接加剧刚修好的超时问题。**必须配合 token 预算控制**。

**工作量**：3-4 天（含测试）

#### F2 客户端超时按模型能力自适应

**为什么做**：刚踩过——90 秒对推理模型不够，我们靠调 `maxTokens` 绕过，但根因没解决。

**怎么做**：
- 用 `llm.resolveModelInfo(provider, model)` 拿到 `reasoning` 元数据（`LlmResolvedModelInfo.reasoning`）
- 推理模型（有 `defaultEffort` 且 `canDisableThinking` 为假）→ 超时放宽到 180 秒
- 普通模型 → 保持 90 秒
- 或者更简单：把超时做成配置项

**为什么优先**：这是已发生过的真实故障，不是假设。

**工作量**：1 天

---

### P1 · 有机制依据，值得做

#### F3 可组合增强项（借鉴 prompt-decorators）

**为什么做**：现在只有「专业提示词 / 仅润色」两档，粒度太粗。用户可能只想加"约束清单"、不想改整体风格。

**设计**：
```
点 ✨ → 菜单
  ├─ 专业提示词（默认）
  ├─ 仅润色
  └─ 增强项（多选）
      □ 补充约束（明确边界、禁止项）
      □ 加输出格式（结构化、可解析）
      □ 加验收标准（怎样算做到）
      □ 加反例（常见错误示范）
```
- 每个增强项是**独立的提示词片段**，可自由组合
- 选中后拼进 system prompt 末尾
- 保持"不改变用户原意"这一底线

**工作量**：4-5 天

#### F4 改写结果的「差异对照」

**为什么做**：用户看不到改了什么，只能整体接受或 ↩ 还原。这对"信任"是硬伤。

**设计**：
- 改写后在草稿下方显示可折叠的 diff（新增/删除）
- 高亮 `[默认：…]` 与 `[请补充：…]`
- 点击差异可局部回退

**工作量**：3-4 天（Client 侧重）

---

### P2 · 有价值但优先级低

#### F5 长草稿压缩（借鉴 LLMLingua 思路）

**场景**：用户粘贴几千字长文要求改写。现在只能拒绝（`maxInputChars`）或硬改。

**做法**：先用一次轻量模型调用抽取"必须保留的实体与约束"，再改写。**注意**：必须复用我们的 `checkFidelity` 保真检查，否则会丢信息。

**工作量**：4 天，且有保真风险，建议后置

#### F6 提示词库 / 一键复用

**场景**：某个改写结果很好，想存下来下次直接套用。

**做法**：本地 JSON 存储 + 菜单里「我的模板」分组。

**工作量**：3 天

#### F7 多候选（一次生成 2-3 版）

让用户选，而不是只给一版。对应 v2 设计稿里的 C 类分叉。

**工作量**：2 天（但要考虑 token 成本翻倍）

## 三、我建议的顺序与理由

```
第 1 步  F2 超时自适应        1 天   ← 已发生的故障，先止血
第 2 步  F1 对话上下文        4 天   ← 唯一明确落后竞品的能力
第 3 步  F4 差异对照          4 天   ← 直接改善信任
第 4 步  F3 可组合增强        5 天   ← 借鉴装饰器，拉开差距
第 5 步  F5/F6/F7            按需
```

**为什么 F2 排第一**：它是**已经发生过**的用户可见故障，不是推测。而且改动小、风险低。

**为什么 F1 排第二**：这是唯一**确定落后**的能力，且竞品证明了这个需求真实存在。

**为什么 F3 排第四**：可组合增强看起来最"亮眼"，但它需要先有上下文感知和差异对照打底，否则用户不知道增强项是否真的有用。

## 四、必须先想清楚的两个约束

### 4.1 token 成本会失控

F1（上下文）+ F3（增强项）+ F7（多候选）全部叠加后，单次改写可能从 4k token 涨到 20k+。

**现在没有任何 token 预算控制**。建议：
- 在 Host 侧估算输入 token，超过阈值时降级（减少上下文轮数 / 关闭多候选）
- 把"本次消耗多少 token"暴露给用户

### 4.2 我们在用一个模型做两件事

改写提示词其实是**两个任务**：
1. 判断用户真正要什么（需要推理）
2. 组织成专业表达（不需要重推理）

现在合成一次调用。v2 设计稿里拆成 Pass 1 / Pass 2 就是因为这个。但拆分会让延迟翻倍——而延迟正是刚修好的痛点。

**这是一个真实的架构权衡，我没法替你做决定**：
- 保持单次 → 快，但分析能力受限
- 拆成两次 → 准，但慢一倍
- 折中：只在"草稿很短且模糊"时才走两段式

## 五、调研中确认的三个「不要做」

| 不做什么 | 为什么 |
|---|---|
| 抄 PromptEnhancer 的**内容** | 它是文生图改写，领域不同，抄了会错 |
| 引入 LLMLingua / DSPy 作为**依赖** | 都是 Python，插件是纯 Node ESM，且 junction 安装无依赖树 |
| 做"提示词市场/云端分享" | 超出插件边界，且引入隐私与运维负担 |

---

## 六、一句话总结

**最该做的不是加更多"智能"，而是补齐两个已经暴露的短板：知道自己处在什么对话里（F1），以及在慢模型上不卡死（F2）。**

其余功能都属于"锦上添花"，等这两个稳住再谈。
