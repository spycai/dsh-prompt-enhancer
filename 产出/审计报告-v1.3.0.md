# dsh-prompt-enhancer v1.3.0 只读审计报告

- 审计对象：`E:\deepseek harmess\01_主项目\dsh-prompt-enhancer\源文件`
- 技术栈：纯 ESM、无构建步骤、无第三方运行时依赖（Host 用 `ctx.llm` / `ctx.connection` / `ctx.webServer`，Client 用宿主 `__ModuleLoader__` + React）
- 代码量：index.js 361 行、client.js 494 行、lib/prompt.js 265 行、test 130 行
- 审计方式：逐文件阅读 + 针对性运行时验证（下列标注「已实测」的条目均有可复现脚本输出）

---

## 1. 总体结论与风险评级

**风险评级：中（可上线给个人用，不宜直接团队推广）**

整体工程质量高于一般随手写的 DSH 插件：纯函数已抽出、14 条单测全绿、错误码稳定、无 XSS 面、无密钥、无第三方依赖。三条架构决策是正确的——数据传输走 connection Fetch 桥（绕开 `dsh-app://` 相对路径问题）、输入用 `<user_message>` 包裹声明为数据、备用 HTTP 路由先 `connection.admit()` 鉴权。

但存在 4 个高优先级缺陷，其中 2 个已被实测复现：

1. **分隔符未转义，提示词注入可突破**（prompt.js:111）
2. **用户选的模式会被配置覆盖**（index.js:176）
3. **provider 与 model 可跨厂商拼接**（index.js:252-268）
4. **上游英文报错直接透传给中文用户**（index.js:230）

这些不是"代码风格问题"，而是**会让功能产出错误结果或给出无法执行的模型路由**的正确性缺陷。

### 已确认无问题（附依据，避免误报）

- **XSS**：全部文本经 `React.createElement` 的字符串 children 渲染，无 `dangerouslySetInnerHTML`、无 `innerHTML`、无 `eval`；模型输出只经 `setDraft()` 变成纯文本。
- **密钥/敏感数据**：无任何密钥读写、无日志打印用户草稿、无外发网络请求（只打本机 `/api` 与 `/prompt-enhance`）。
- **依赖漏洞**：运行时零第三方依赖；junction 安装也意味着不会引入传递依赖树。
- **鉴权**：`/prompt-enhance` 走 `connection.admit()`，**已实测**匿名请求返回 401 `UNAUTHORIZED`；`/api` 路径继承宿主浏览器会话鉴权。
- **请求体上限**：两条入口都有 512KiB 限制，超限 `BODY_TOO_LARGE`。
- **取消链路完整**：`AbortController` → `request.signal` → `ctx.llm.stream({ signal })` 全程透传，客户端 90s 超时兜底。
- **并发覆盖**：`draftRef` 快照比对，草稿变了不覆盖而转「待应用」，逻辑正确。
- **降级**：`useInput`/`setDraft`/`useProjection` 缺失时都有 `typeof` 守卫，不会抛错白屏。

## 5. 一句话结论

**能日常用，但当前版本带 4 个正确性缺陷，其中 2 个会直接产出错误结果（模式被覆盖、路由跨厂商）和 1 个会让安全防线失效（分隔符注入）。** 这 4 项合计约 2 小时工作量、零架构改动、零新依赖，修完再谈增强；不修则不适合团队推广 —— 因为故障表现为"功能偶尔不正常"，用户很难归因到插件。
