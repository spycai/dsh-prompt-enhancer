### M-4 上游异常路径会把英文内部信息透传给用户

**证据**（脚本复现）：

```
new Error('upstream vendor internal error: request_id=abc-123 token=sk-xxx')
  → failureOutcome()
  → { status: 502, code: 'SOME_VENDOR_ERROR',
      message: 'upstream vendor internal error: request_id=abc-123 token=sk-xxx' }
  → 泄露内部信息: true
```

**根因**：[index.js:350-357](E:\deepseek harmess\01_主项目\dsh-prompt-enhancer\index.js#L350) 只清洗了 `finish.reason.failure`（模型流内返回的失败）；但如果 `ctx.llm.stream()` **本身抛异常**（网络层、适配器层、初始化失败），异常会走到 [index.js:181](E:\deepseek harmess\01_主项目\dsh-prompt-enhancer\index.js#L181) → `failureOutcome()`，而 [lib/prompt.js:420-427](E:\deepseek harmess\01_主项目\dsh-prompt-enhancer\lib\prompt.js#L420) 直接把 `error.message` 塞进响应。

技能文档里点名的坑「上游英文报错直接透传用户 → 应 code 映射，原文只进日志」，**只修了一半**。

**测试缺口**：`test/enhance.integration.test.mjs` 的 14 条覆盖了 `finish.reason.failure`，**没有覆盖 `llm.stream()` 抛异常**（已用 grep 确认）。

**修复建议**：
- `failureOutcome()` 对非白名单 code 一律用 `llmFailureMessage(code)` 或固定安全文案，`error.message` 只 `console.warn`
- 补一条集成测试：假 `ctx.llm.stream` 抛带 `request_id`/`token` 的异常，断言响应体不含这些串、且 code 稳定

### M-5 `applyPending()` 记错「原文」，↩ 还原会还原到错误内容

**证据**（[client.js:352-361](E:\deepseek harmess\01_主项目\dsh-prompt-enhancer\client.js#L352) 对照 [client.js:336-350](E:\deepseek harmess\01_主项目\dsh-prompt-enhancer\client.js#L336)）：

```js
// applyResult（正确）           // applyPending（错误）
setOriginal(snapshot)          setOriginal(draft)
```

`pending` 只在 `setPending({ text: payload.text })` 时保存了**结果文本**，没保存 `snapshot`。

**复现路径**：
1. 用户输入 A，点改写 → 结果 B 返回前，用户把草稿改成 A′
2. `draftRef.current !== snapshot` → 走 `setPending`，提示「草稿已被修改，再点一次应用」
3. 用户再点 → `applyPending()` 里 `draft` 此刻是 **A′**
4. `setOriginal(A′)` 把"原文"记成 A′
5. 之后点 ↩ 还原 → 还原成 A′，而不是用户最初写的 A

**影响**：低频但数据正确性有问题，用户会丢原文。

**修复建议**：`setPending({ text: payload.text, snapshot })`；`applyPending()` 用 `setOriginal(pending.snapshot)`。补一个状态机单测（或至少在注释里写清三态）。
